# Agent多轮会话阶段方案

日期：2026-11-01。状态：用户已确认MySQL方案，已实施并完成测试库迁移、定向验证和真实DeepSeek复测；最终回归及打包见第三十五阶段说明。没有新增依赖，开发库DDL尚未执行。

## 目标与现有依据

目标：同一用户在同一会话追问“第一笔什么时候过期”等问题时，能利用前文理解所指订单；当前订单状态仍通过本人订单工具重新查询。阶段包括创建会话、会话归属、有限历史、清空历史及必要验证，不包含SSE、前端页面、长期摘要或多Agent。

现有入口为AgentController.chat与TradeAgentService.chat(long userId, String message)。每次调用重新创建SystemMessage和UserMessage；工具调用历史仅在当前循环内使用，没有跨请求存储。已有SecurityConfig对POST /api/agent/chat要求登录，保留CSRF；其他未列出的请求默认拒绝。SharedSessionConfiguration仅在shared-session profile启用Redis登录Session，登录Session不等于Agent对话。

RAG阶段的未提交改动原样保留，不在本阶段自动提交或推送。密钥与默认开关保持现状。

## 存储方案与建议

建议复用现有MySQL、MyBatis和按编号维护的SQL脚本，新增会话与成功轮次数据。重启后可继续使用尚未过期的会话，可直接查询记录排查问题，不增加依赖或新服务。成本是新增数据库表和迁移步骤。

替代方案为复用Redis保存短期对话，利用TTL自动过期；但会话可用性将依赖Redis，且需另行处理并发更新和清空冲突。当前阶段优先MySQL，数据库迁移仅新增本阶段表，不覆盖既有数据。

## 拟新增接口

以下是本阶段拟定义的新接口，不是现有能力：

- POST /api/agent/conversations：创建属于当前登录用户的会话，返回随机UUID conversationId。
- POST /api/agent/conversations/{conversationId}/messages：向本人会话发送message，响应复用现有AgentChatResponse结构。
- DELETE /api/agent/conversations/{conversationId}/messages：清空本人会话历史，保留会话编号。
- 原POST /api/agent/chat保持单次无记忆行为，兼容既有调用与测试。

新增接口显式加入SecurityConfig允许范围，要求Session登录，写请求继续要求CSRF。userId只取认证主体，不接受客户端指定。会话不存在、已过期或不属于本人统一返回404，检查失败时不得访问模型或执行订单工具。

## 历史与预算

每个会话最多保留最近6个完整成功轮次，每次构建提示最多加入24,000字符的历史内容，超限时按完整轮次淘汰最旧记录；不截断工具调用与结果对。该限制是字符预算，不宣称精确Token控制。单个轮次超过预算时不将其纳入后续上下文，必须在文档和测试中说明该边界。

保存服务端产生的消息角色、用户问题、模型工具调用、配对工具结果和最终回答，客户端不能提交历史或系统消息。只在完整回答成功后保存一轮；超时、工具失败或模型失败不保存半轮，也不覆盖先前历史。模型和工具次数预算沿用现有实现，失败如实返回，不以空历史降级。

每次请求重新生成当前系统提示、查询时间和可信ToolContext。历史消息及工具结果作为历史数据，不升级为系统指令。历史来源不混入本次knowledgeSources或sources；这两个响应字段继续只记录本次实际工具执行的来源。

历史仅帮助解析指代，订单金额、状态和截止时间等当前事实必须重新查询本人订单工具，不能把历史查询结果当成实时数据。不得将地址、手机号、运单或密钥加入新增记忆；当前AgentOrderSummary已过滤这些字段。

会话暂定24小时无活动过期，每用户最多10个未过期会话；创建及访问时处理该用户过期数据，避免会话数无限增加。不实现会话列表或后台管理界面。历史保存在应用数据库，会随既有备份策略保留；本阶段不宣称已实现独立的数据生命周期管理系统。

## 同会话并发

同一会话只允许一个生成请求执行，并发追问返回409，不混合消息顺序。数据库只用短事务领取或提交生成资格，不在等待模型网络响应期间持有数据库事务或行锁。

生成资格带有效期与版本；异常退出后可过期恢复。清空历史使旧版本失效，进行中的旧请求不得将历史写回或成功返回过时会话结果。提交阶段校验会话归属、版本、资格和过期时间。不同会话可独立执行。
