# 第十一阶段设计：可靠消息与订单超时

日期：2026-10-18。

状态：设计已确认并于2026-10-18实施完成。验收以README、实施计划和第十一阶段学习稿为准；本文保留下方原始实施前盘点的时间边界。

## 1. 目标与当前依据

高级阶段以七张参考简历和 hy0713/ecommerce-order-system 固定提交 3e49d89ccd7dff90978784e4be273d8952bf385a 为比较材料。本阶段只实现一个消息场景：可靠投递订单超时检查消息。

现有订单在创建时扣商品库存，活动订单另扣活动名额；订单自身保存 expiresAt，支付期限15分钟。相同 userId/requestId 先返回原订单，比较商品、数量和 nullable activityId。关闭订单必须满足 PENDING_PAYMENT 且 expires_at <= cutoff，只有条件状态转换成功才归还活动名额、商品库存，同一MySQL事务处理；提交后删除商品列表缓存。

现有 OrderTimeoutScheduler 每轮结束后等待30秒扫描，单轮100条候选，跨Bean调用 OrderService.closeExpiredOrder。原关闭逻辑继续作为唯一业务执行入口。

新增能力：订单和待发送事件原子保存；独立发布、Broker确认、失败重试；等待队列到期后消费；重复消息安全；消费失败留痕；数据库扫描保留。

不在本阶段拆服务、异步创建订单、Redis预扣库存、真实支付、购物车、优惠券或AI。不修改用户接口和订单状态含义，不新增第二份库存权威数据。

## 2. 方案比较与选择

| 方案 | 作用与取舍 |
|---|---|
| 提交后直接发送 + 扫描 | 改动少，但订单提交后进程退出或消息发送失败，只能依赖扫描，没有待发送记录 |
| 本地消息表 + TTL/死信 + 扫描（本稿采用） | 订单与发送意图原子落库，投递可重试；学习队列、确认、重复消费及补偿，但多出持久化和投递任务 |
| 本地消息表到期才投递到普通队列 | 不需TTL链路，但延迟主要由投递扫描决定；本阶段不并行实现两套机制 |

本地消息表也称Outbox。本项目仍是单体，库存归还继续使用数据库本地事务；不照搬参考微服务的远端库存补偿表。

## 3. 主流程

```text
POST /api/orders
  → 原用户锁、幂等、活动与库存处理
  → 插入trade_order，回填订单id
  → 在同一事务插入order_timeout_outbox
  → 登记商品缓存提交后失效
  → MySQL提交
  → 返回原订单响应

独立消息投递任务
  → 扫描可重试的PENDING记录
  → 单条独立事务锁定事件
  → 发送到RabbitMQ等待队列
  → 收到Broker ACK且没有不可路由退回，标记SENT
  → 发送失败/退回/NACK/确认超时，记录错误并安排下次尝试

等待队列TTL到期
  → 死信交换机
  → 到期处理队列
  → 消费者调用OrderService.closeExpiredOrder(orderId, 当前时间)
  → 原条件状态转换、双归还、提交后缓存失效
  → 成功返回后确认消费

原数据库扫描
  → 继续按expires_at扫描
  → 调用同一个关闭方法
```

用户下单线程不等待RabbitMQ。Redis缓存提交后删除失败的现有边界保留：数据库可能已经提交，Outbox记录也已经存在；同请求标识重试仍返回原订单。

## 4. 拟新增的数据结构

以下均为本阶段拟新建标识，不是对现有表字段的描述。

迁移：sql/007_order_timeout_outbox.sql。新增专用表 order_timeout_outbox，不建立通用事件总线框架。

| 字段 | 含义 |
|---|---|
| id | 事件自增编号，重复投递保持同一编号 |
| order_id | 原订单编号，唯一约束；一单只登记一个超时事件 |
| expires_at | 创建事件时保存的原订单支付截止时间 |
| status | PENDING待投递、SENT已获Broker接收确认 |
| attempt_count | 已提交保存的发送尝试次数；进程退出或本地回滚可能使一次物理发送未计入，不作为完整发送审计 |
| next_attempt_at | 下一次允许尝试的时间 |
| last_error | 最近一次失败的有限长度错误摘要，成功后清空 |
| created_at | 登记时间 |
| sent_at | 标记成功投递的时间，未成功为空 |

新增唯一索引(order_id)，候选索引(status, next_attempt_at, id)。事件保存与订单插入共用事务；订单或事件插入任一失败则一起回滚。幂等提前返回分支不新增事件。

消息正文固定为 eventId、orderId、expiresAt 三个字段，不传密码、用户凭证、库存值或整份订单。消费者用orderId操作，数据库订单的截止时间与状态是最终依据。消息中的expiresAt用于追踪，不授权提前关闭。

SENT只表示Broker已确认接收且本次无路由退回，不表示已消费，也不表示订单已关闭。

已有历史待支付订单由原扫描覆盖；本阶段不回填历史消息。新表进入测试夹具清理及开发库基线核对，禁止靠清空开发库准备验证。

## 5. 发布任务、事务与重复发送

默认每轮完成后等待3秒，最多读取20条到期PENDING候选。扫描本身不授予执行权。

逐条通过另一个Spring Bean的公共事务方法处理：按id、PENDING和next_attempt_at条件执行FOR UPDATE SKIP LOCKED，避免两个投递者同时处理同一条记录。网络等待只占用事件行事务，不持有用户、活动或商品锁；单次确认等待设为2秒。

使用publisher confirm、mandatory和退回处理，只有ACK且没有路由退回才标SENT。不能仅凭发送方法返回就标记成功。ACK、NACK、超时和退回的准确API与顺序将在依赖下载后依据当前Spring AMQP版本核对。

失败记录仍为PENDING，增加尝试计数，记录错误，重试间隔依次为5、10、20、40秒，之后每次60秒。Broker长期不可用时保留发送意图；不设置一个到期即永久放弃的生产端重试上限。数据库异常向外传播，使单条事务回滚；不伪装成成功。

确认后写SENT前进程退出、或本地提交失败时，消息可能重复发送。确认超时也可能是Broker已收而确认未到，必须允许重复。目标是可恢复的至少一次投递意图，不宣称恰好一次。

任务每次处理一条并提交，已提交条目不因后续条目失败一起回滚；数据库持续异常由任务日志暴露并在后续轮次重试。

## 6. RabbitMQ拓扑与到期语义

拟新建命名空间limited-trade，避免与参考仓库或其他项目冲突：

| 对象 | 拟定名称与用途 |
|---|---|
| 入口Direct交换机 | limited-trade.order-timeout.exchange |
| 等待队列 | limited-trade.order-timeout.wait，队列TTL为900000毫秒 |
| 等待路由键 | order-timeout.wait |
| 到期Direct交换机 | limited-trade.order-timeout.dlx |
| 到期处理队列 | limited-trade.order-timeout.ready |
| 到期路由键 | order-timeout.ready |
| 失败Direct交换机 | limited-trade.order-timeout.failed.exchange |
| 失败归档队列 | limited-trade.order-timeout.failed |
| 失败路由键 | order-timeout.failed |

交换机、队列持久化，消息设为持久化。等待队列到期死信到ready；ready消费重试耗尽后拒绝回队，通过其死信配置进入failed。无需延迟消息插件。

队列TTL从实际进入等待队列起算，不从订单createdAt起算。延迟投递或重试会使MQ触发晚于原expiresAt；消费者积压同样会延后处理。因此保留数据库扫描，不宣传到期立即关闭，也不把MQ触发时间作为支付期限。

初版不实现每消息不同TTL，避免将不同到期时间的队列头阻塞问题引入当前固定15分钟场景。未来可另行比较到期Outbox投递、时间桶或其他延迟机制。

持久化和入口确认不等于端到端绝不丢消息；Broker故障、死信转发问题等仍由数据库扫描覆盖订单关闭。

## 7. 消费与业务幂等

监听器不重复编写状态转换和库存归还。消息到来后，调用现有事务方法closeExpiredOrder(orderId, LocalDateTime.now().withNano(0))。

| 数据库情况 | 处理 |
|---|---|
| 已到期且PENDING_PAYMENT | 原条件UPDATE成功，归还数量并提交 |
| PAID、CANCELED、CLOSED | UPDATE为0，正常确认，不归还 |
| 重复消息或扫描已经处理 | 同上，不能因重复再归还 |
| 消息提前到达 | expires_at条件不满足，不提前关闭；原扫描仍处理真正到期订单 |
| 库存/名额归还SQL失败 | 原事务回滚，消费报错并重试 |
| 提交后缓存删除失败 | 数据库可能已提交；后续重投按已关闭状态正常退出，缓存仍受原30秒有效期约束 |

采用容器AUTO确认：业务调用正常返回后由容器确认，不与Redis或MySQL自动构成一个分布式事务。数据库已经提交但消费确认前进程退出时可重投，靠订单条件状态转换防止重复归还。

消费失败最多尝试3次（含首次），间隔1秒、2秒；仍失败则拒绝且不回原队列，进入failed留痕，不无限热循环。恢复后可通过运维重投同一条消息；本阶段不新增失败消息管理页面。

MQ是系统边界，无法转换成约定消息结构的消息不得执行交易操作，应进入失败处理流程。具体转换异常重试/拒绝行为必须在集成验证中确认，不能仅凭配置存在宣称覆盖。

## 9. 验收标准

只报告用例目的、结果和证据，不给学习者展开测试代码。

1. 首次创建普通/活动订单各生成一个事件；幂等重试不增加事件。
2. 故意使事件插入失败，确认订单、商品库存、活动名额一起回滚。
3. Broker不可用时订单及事件可以提交；恢复后PENDING事件重试成功。
4. 不可路由、NACK或确认超时不能误标SENT。
5. 两个投递者竞争同一事件、确认后本地状态失败等场景，允许重复消息但不重复归还。
6. 到期消息关闭待支付订单；重复消息、已支付、已取消、提前消息不错误变更状态。
7. 消费异常重试耗尽后消息进入failed，修复后重投可按数据库现状处理。
8. 关闭消费者后仍可由原扫描关闭订单；消息延迟或积压不延长支付接口的原截止时间。
9. 取消/关闭/支付竞争保留合法终态，库存及活动名额各只归还一次。
10. 运行完整既有用例与新增用例；检查测试数据、专用队列/键清理以及开发库公开字段基线。

首次接入允许隔离验证环境缩短等待队列TTL；业务关闭仍按真实订单expiresAt判断。验证使用独立RabbitMQ虚拟主机/命名空间，不操作其他项目队列，不清空Redis或开发库。
