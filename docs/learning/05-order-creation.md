# 第五阶段：创建订单、库存扣减与本人订单查询

本文件记录第五阶段的代码与边界。第六阶段新增了模拟支付、主动取消和订单时间字段，参见 `06-order-payment-cancel.md`。

## 目标与当前边界

一个订单购买一种商品，可购买多件。下单时扣减可售库存，并保存名称、单价、数量和金额快照。订单状态为 PENDING_PAYMENT。

本阶段没有支付、取消或自动超时关闭。expires_at 只记录下单后15分钟的截止时间，不会自行触发任务。

## 先读一次下单

客户端发送：

```json
{"productId":1,"quantity":2,"requestId":"7f1b2d58-917d-4c05-8a85-e190a7e53739"}
```

requestId 标识一次下单操作，上例使用 UUID 字符串，满足代码规定的 ASCII 字母、数字、下划线或连字符格式。

Controller 从 PlatformUserDetails 取得用户编号，调用 Service。客户端额外传来的 userId 或金额不会成为下单依据。

Service 的顺序：

1. 进入 Spring 管理的事务。
2. 按主键锁住当前用户行。
3. 查该用户的 requestId 是否已有订单。
4. 若已有，商品和数量相同则返回原订单；不同则409。
5. 若没有，从数据库查询商品；找不到则404。
6. 执行带上架状态和库存条件的扣减 SQL；影响0行则409。
7. 用数据库商品名称和价格计算订单金额，保存待支付订单与15分钟截止时间。
8. 事务成功提交，释放锁，返回201。

金额使用 BigDecimal 精确乘法。订单总额采用 DECIMAL(20,2)，范围比 DECIMAL(10,2) 的单价更大，用于容纳正整数购买数量的乘积。时间使用当前主机的 LocalDateTime，按 DATETIME 秒精度保存；跨时区部署尚未验证。

## 为什么不能只先查一下有没有重复请求

两个同一用户的并发请求，可能同时查询到“没有订单”，再各自扣库存和插订单。唯一约束可以阻止重复记录，但应用还需要合理处理事务与重复响应。

当前选择让同一用户的下单事务串行：

```sql
SELECT id FROM app_user WHERE id = #{id} FOR UPDATE
```

锁在同一个事务中持有到提交或回滚。第二个相同用户的请求取得锁后，再查询已经提交的订单，因此能够直接返回原订单，即使库存已被第一单耗尽，也不再尝试扣减。

这会限制单个用户的并发下单吞吐，是本版为了简单、可解释而做的取舍。不同用户锁的是各自用户行，不等于全平台串行。这里依赖数据库行锁，不使用只在单个 JVM 内有效的 synchronized 来保证业务幂等。

数据库同时通过 `(user_id, request_id)` 唯一约束保护记录唯一性。同一用户主动再次购买要使用新 requestId；同一次购买的重试使用原 requestId。

## 库存 SQL 为什么这样写

```sql
UPDATE product
SET stock = stock - #{quantity}
WHERE id = #{id}
  AND status = 'ON_SALE'
  AND stock >= #{quantity}
```

条件判断与扣减由 MySQL 的同一条更新完成。不能把“先在 Java 里看库存够不够”当作并发保证。

扣减与订单插入位于同一事务。如果后续插入发生异常，事务会回滚前面的扣减；当前未进行数据库故障注入测试，不把这种故障场景描述成已实测。

## 如何保证只读本人订单

详情查询的条件包含：

```sql
WHERE id = #{id} AND user_id = #{userId}
```

userId 来自登录身份，不从查询参数读取。查不到统一404，不向调用者区分“没有该订单”和“属于别人”。订单列表同样按当前用户过滤。

## 验证结果

- 首个接口测试在订单接口缺失时因403失败；实现后离线打包，全量57个测试通过。
- 订单接口17个测试覆盖服务端定价、身份来源、成交快照、归属、重复请求、库存不足、下架与非法输入。
- 并发测试使用真实 MySQL、10个线程提交20个请求；不同用户竞争5件库存仅生成5单，库存为0。
- 同一用户对库存仅1件的商品并发重试20次，得到相同订单编号，只扣1件。
- 事务测试回滚；并发测试使用已提交的独立夹具，并按明确编号清理。最终测试库订单、商品、用户均0行。
- 没有执行开发库 HTTP 下单，开发库订单0行，原三条商品和两个账号保留。

这些是正确性证据，不是压力测试或生产性能结论。
