# 第二十一阶段：完整现有业务前端

## 页面入口与范围

正常启动Spring Boot应用后访问 http://localhost:8080/ 。前端与API同源，不另开前端服务，不使用CDN，不安装Vue/React或Node构建依赖。源码位于src/main/resources/static，由Boot直接提供资源。

| 导航/入口 | 已接入操作 |
|---|---|
| 登录/注册 | 注册、登录、读取身份、退出；角色来自/api/auth/me |
| 发现商品 | 在售商品、分类、关键词搜索、分页、加购物车、普通立即购买 |
| 限量活动 | 浏览活动、规则与名额、领取活动券、选择本人券和地址购买 |
| 购物车 | 数量修改保存、移除、勾选、选择地址、多商品结算；未保存数量时阻止结算 |
| 收货地址 | 新增、修改、删除确认、设默认 |
| 我的券 | 规则、使用区间、过期、占用/核销及关联订单 |
| 我的订单 | 列表、详情、成交金额/商品/地址/优惠快照、物流、模拟支付、取消、确认收货 |
| 管理中心 | 仅ADMIN可见；分类创建/重命名，全部商品创建/编辑/上下架，活动和券创建/查看，订单筛选分页、详情和发货 |

立即购买和结算页面要求选择地址；不改变后端对无地址历史订单的处理。购物车不使用活动券，活动单独购买。商品编辑无库存修改接口、活动与券无修改接口、系统无退款接口，因此不做这些操作的假按钮。

## 文件如何协作

- index.html：页面骨架、导航、身份区、消息区、主要内容和原生dialog弹窗。
- assets/styles.css：浅色商店布局、商品/活动卡片、表单、订单和管理列表，适配移动宽度。
- assets/api.js：同源fetch、CSRF、HTTP错误、会话代次及下单未确认意图。
- assets/ui.js：安全DOM构造、通用表单弹窗、字段/按钮/分页/格式化。业务文字创建文本节点，不拼入innerHTML。
- assets/app.js：用户页面、登录状态、hash导航、订单动作；路由和异步弹窗检查页面版本与会话身份。
- assets/admin.js：管理侧表单与列表，复用API和UI模块。

没有前端路由服务器重写需求，地址使用#products、#activities、#cart、#addresses、#coupons、#orders、#admin。默认首页为商品页。

## 后端只补哪些入口

GET /api/activities：ActivityController→ActivityService→ActivityMapper.findAll，按编号降序返回已有活动。原来只有按编号读取，页面无法浏览全部活动。

GET /api/admin/products：AdminProductController→ProductService→ProductMapper.findAllProducts，返回含下架商品的列表；沿用/api/admin/**仅ADMIN规则。创建商品默认下架，因此不能用公开在售列表代替管理列表。

SecurityConfig仅允许GET /、/index.html、/assets/*.js、/assets/styles.css；API权限与CSRF继续生效。没有表迁移、新依赖或新的交易写规则。

## 请求、身份和错误

登录使用application/x-www-form-urlencoded，注册和业务正文使用JSON。每次写入先GET /api/auth/csrf取当前令牌，避免登录/退出轮换后沿用旧令牌。不把密码、身份或令牌存到Web Storage，不自动重放写请求。

401清理当前身份和私有页面；403、409、429（含Retry-After）、503和网络失败展示明确提示。用户名重复有独立注册提示；页面选项、数值和时间先做浏览器基本校验，最终合法性仍由后端判断。

api.js记录会话代次，登录/退出成功及身份变更时推进；等待CSRF期间会话变化就取消旧操作，不把旧操作提交到新会话。过期的旧401不能覆盖新身份。异步订单详情、购买弹窗和券规则查询在展示前检查页面/会话版本，避免会话清理后重新显示旧账号地址。

## 成功与错误提示

成功消息由ui.js的notify统一管理，3秒后自动隐藏。新消息先取消旧计时器，再设置自身计时器，防止旧消息提前关闭新消息；错误提示保留供用户阅读。登录成功、保存、领取成功等都使用这一逻辑。定向浏览器notice场景验证了登录成功自动关闭、连续成功消息计时重置和错误消息不被旧计时器关闭。

## 下单幂等与不确定结果

使用crypto.getRandomValues生成16随机字节的32位十六进制requestId，满足后端1—64位规则，在普通HTTP上下文也可使用。sessionStorage按用户编号保存当前未确认意图：路径、商品/地址/券编号等购买参数和原requestId，不保存完整地址或密码。

网络或5xx不能证明订单没成交，所以保留原请求，提供“使用原请求重试”和“查询我的订单”。参数改变时不会拿同一个requestId提交另一笔购买；查询订单匹配原requestId后清除待确认标记。

首次请求明确4xx拒绝时可修正；如果已经有未知结果，重试在认证/CSRF/限流环节收到401/403/429仍保留原标识，因为尚未进入订单幂等查询。当前订单入口在用户锁内查询既有订单后返回的业务404/409可释放该意图。不会在响应丢失后直接生成新编号重复购买。

## 可直接使用的开发演示数据

sql/demo_catalog.sql只在开发库手动执行，不参与应用启动和测试库初始化。新增4个分类、8个在售商品、3场限量活动和3种可领取的满减券，名称统一使用“演示·”前缀。键盘满199减20、保温杯满49减5、台灯满99减10，分别绑定对应商品活动，单件即可满足门槛。

活动与券在首次导入后有效30天，券的领取和使用时间与活动一致，每人每种券仍按现有规则限领一张。使用真实开发库验证数量、当前时间有效性、库存与活动名额、满减金额规则；再次执行后全部演示记录不变，原有商品等记录保持不变。不预建用户订单、私人地址或已领取券。
